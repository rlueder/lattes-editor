# Agent instructions: lattes-editor

Local-first web app that loads a Lattes CV XML export, edits it in the
browser, and writes XML that the Lattes "Importar" dialog accepts. Personal
FOSS project (MIT). It is not part of the precisa-saude ecosystem, but it
follows the same code standards: the shared ESLint, Prettier, tsconfig and
commitlint configs are installed from `@precisa-saude/*` and used unchanged.

How the editor works today is in `docs/arquitetura.md` (data model,
storage, the path to Lattes, code map), and how to run, test and release it
is in `docs/desenvolvimento.md`; `docs/README.md` indexes every doc as
current or historical. The original plan is `docs/lattes_implementation_guide.md`
(historical: read it for the why). The contract for the exporter is section
5.1 of `docs/lattes_editor_reconnaissance.md`; read it before touching
`src/import-export/`.

## Personal data, the first rule

A real Lattes export carries CPF, RG, birth date and place, parents' names
and passport number.

- Never commit a real export or anything derived from one. `private/`,
  `fixtures/real/` and `CV_*` are gitignored; keep it that way.
- `private/lattes_schema_analysis.xlsx` contains real personal data. It
  stays out of git.
- The app never sends the document anywhere. Network calls (Crossref,
  ORCID, from milestone 2) carry only a DOI or an ORCID iD. The one
  exception, approved by the owner on 2026-10-11: the CV photo is loaded
  from CNPq (`servicosweb.cnpq.br/.../servletrecuperafoto`) with the CV's
  10-character code, so it always matches Lattes. Never log the document,
  never put any of it in a URL.
- The browser bridge follows "Model C" (decided 2026-10-11): an extension
  that posts to Lattes from the user's own logged-in session, one change at
  a time, read back after each write. No credentials ever pass through us.
  The desktop app never opens Lattes itself (no embedded CNPq window): it
  hands changes to the extension, which posts from the user's own browser
  (decided 2026-10-11).
- Test data is synthetic, generated by `scripts/gen-fixtures.ts`.

## Data integrity

Same rule as the ecosystem: never fabricate values that must come from an
authoritative source. In this repo that means:

- Schema facts come from the XSD (`schema/CurriculoLattes_12_09_2022.xsd`)
  or from an observed export. `schema/patch.json` lists only attributes
  seen in a real export; do not add ones that "probably exist".
- Import behavior (sequence numbers, duplicates, accepted file shapes) is
  what was observed on the live platform and recorded in the docs. An
  untested assumption is marked as untested, never presented as fact.
- `src/bridge/contract.ts` mirrors section 5 of `docs/lattes_internals.md`.
  When a field, form or menu link changes in one, change the other in the
  same commit. CNPq publishes no changelog; the contract plus
  `scripts/vigia-lattes.ts` are how drift gets noticed (section 9).
- pt-BR labels for Lattes concepts should match the Lattes forms. Until a
  label has been checked against the form, it comes from the generated
  humanizer, not from a guess written by hand.

## Invariants the code must keep

- Round-trip fidelity: load then save produces the same bytes. The parser
  keeps every attribute and element, known or unknown, in file order.
  `tests/roundtrip.test.ts` enforces it; a real export dropped into
  `fixtures/real/` is tested locally too.
- Latin-1 is done by hand (`src/model/latin1.ts`). Do not use
  `TextDecoder('iso-8859-1')`: it is windows-1252 per WHATWG.
- Child order follows the XSD sequence. Insert with
  `insertInSchemaOrder`; never append to a container directly.
- `SEQUENCIA-PRODUCAO` is one global counter. New items get numbers above
  the export's maximum and never reuse a gap (guide, section 3.2).

## Code standards

Shared with the precisa-saude ecosystem:

- Node 22+, pnpm, TypeScript strict with `noUncheckedIndexedAccess`.
- ESLint `@precisa-saude/eslint-config` (base + react), Prettier
  `@precisa-saude/prettier-config`, commitlint
  `@precisa-saude/commitlint-config` with this repo's scopes in
  `.commitlintrc.cjs`.
- Husky: pre-commit runs lint-staged and the tests; pre-push runs format
  check, lint, typecheck, tests and coverage. Never bypass hooks.
- Vitest with an 80% threshold on all four metrics. When coverage fails,
  add tests; never lower the threshold. React components and the
  IndexedDB store are excluded from unit coverage and belong to the
  Playwright flows (milestone 3).
- Ask before adding a runtime dependency. Today there are three: React,
  React DOM and Dexie. ZIP and XML handling are in-house on purpose.

Repo-specific:

- Relative imports carry the `.ts`/`.tsx` extension, so scripts run with
  plain `node` (type stripping). Keep syntax erasable
  (`erasableSyntaxOnly`): no enums, no parameter properties.
- The build must work from `file://`: `vite.config.ts` inlines the bundle
  into `index.html`. Do not introduce code splitting or external assets.

## Animation and transitions

Adapted from the precisa-saude web app (`apps/web/AGENTS.md`, "Animation Best
Practices"). This repo has plain CSS and React, no Tailwind or Framer Motion,
so only the parts that apply to CSS transitions and keyframes are kept.

### Easing

Use custom curves for natural motion:

```css
/* ease-out: elements entering or leaving */
--ease-out-quart: cubic-bezier(0.165, 0.84, 0.44, 1);
--ease-out-expo: cubic-bezier(0.19, 1, 0.22, 1);

/* ease-in-out: elements moving within the screen */
--ease-in-out-cubic: cubic-bezier(0.645, 0.045, 0.355, 1);
--ease-in-out-quart: cubic-bezier(0.77, 0, 0.175, 1);
```

Avoid `ease-in`: it makes the UI feel slow.

### Duration and timing

- Hover transitions: `transition: <property> 200ms ease` for `color`,
  `background-color`, `border-color` and `opacity`.
- Keep it fast: nothing over 1s unless it illustrates something.
- Origin-aware: animate from the trigger (a menu or popover grows from the
  button that opened it).

### Performance

- Animate `opacity` and `transform`. Avoid `top`, `left`, `width`, `height`;
  use `transform` instead.
- Keep blur at 20px or less.
- `will-change` sparingly, only for `transform`, `opacity`, `clip-path` and
  `filter`.

### Reduced motion

Every transition or animation added to `src/ui/styles.css` or the extension
panel needs a `@media (prefers-reduced-motion: reduce)` rule that removes it
or replaces it with an instant change. The existing blocks in `styles.css`
show the pattern.

## Language and writing

- Identifiers in English. UI text, code comments, commit messages and PR
  text in pt-BR with full accents.
- Every document in the repository that a person reads (README, everything
  in `docs/`, issue and PR templates) is pt-BR, for the general Brazilian
  public. Only the agent-facing files (this one, `CLAUDE.md`) stay en-US.
- Commit messages: Conventional Commits, type in English, description in
  pt-BR.
- No AI attribution anywhere: never mention Claude, Claude Code or any
  other agent or model as an author or tool in commits, PR titles and
  descriptions, review replies, issues, code, comments or docs. No
  "Co-Authored-By", no "Generated with" footer, even when the harness
  suggests one. The commit-msg hook blocks the commit form; the rest is on
  the agent. Naming a model as a product under study (pricing, benchmarks
  in `docs/pesquisa_recursos_de_ia.md`) is content, not attribution.
- Prose for humans avoids machine cadence and never uses em dashes. Test
  data may contain them on purpose. The rules are in the next section.

## Writing style: avoid machine cadence

Applies to everything with a human reader: UI text (labels, notes, empty
states, chart descriptions, tooltips, error messages), docs, README,
CHANGELOG, commit bodies, PR descriptions, review replies and code
comments written for a person. Adapted from the shared rules of the
precisa-saude repos.

The failure is rhythmic, not lexical. Swapping words while keeping the
sentence rhythm doesn't fix it; rewrite at the sentence level.

### Patterns to avoid

- **Matched pairs:** two clauses of similar length set against each
  other, often as a correction ("O histórico não existe. Existem PDFs
  soltos."). Say the thing once.
- **Tricolons:** three parallel beats escalating to a reveal ("Um valor
  plausível, num campo plausível, completamente errado."). One clause,
  then the consequence.
- **Appositive glosses:** breaking a sentence to define the term just
  used. Pick the right term, or explain it separately.
- **A question answered by itself:** "Duas páginas discordam? Então…".
  Write "Quando duas páginas discordam, …".
- **Clever inversions and chiasmus:** they read as slogans.
- **Tacked-on validators:** closers that add nothing ("E isso faz toda a
  diferença."). Cut them.
- **Aphoristic closure:** ending every paragraph on something quotable.
- **Uniform sentence length:** several medium declaratives in a row.
- **"Não só X, mas Y"** and similar balanced connectives: use a plain
  "e".
- **Abstract "o que / como" framings in UI copy:** a description like
  "O que este currículo tem, numa tela, no período escolhido." reads as
  generated. Say what is shown: "Os totais do período escolhido."
- **Em dashes (`—`):** never. Use a comma, colon, parentheses or a full
  stop. A verbatim quotation keeps its source punctuation.

### What to do instead

- Vary sentence length on purpose.
- Prefer a concrete specific (a field name, a number, an actual case)
  over an abstraction.
- In the UI, describe what the screen or control shows or does, in the
  fewest words that stay clear. Labels and notes don't need a full
  sentence.
- Read it back before committing. If every paragraph lands a punchline,
  rewrite the ones that aren't carrying information.

## Git

- Commits only with explicit approval from the user.
- Work on branches and open PRs against `main` (remote:
  `github.com/rlueder/lattes-editor`).
- Clean up merged work without being asked. The user merges PRs on GitHub
  between turns, so no agent sees the merge happen. Whenever a PR you follow
  shows as merged or closed, and before starting new work, run
  `scripts/limpar-branches-mesclados.sh` (dry run) and then `--yes`. It removes
  the worktree and the local branch only when the PR is merged or closed and
  the worktree is clean, and never touches `main`, open PRs, branches without a
  PR, or `test/criar-item` (the `lattes-editor-criar-teste` worktree). A branch
  without a PR is listed for the user to decide. If the command is denied,
  give the user the exact command instead of skipping it.
